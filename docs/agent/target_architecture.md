# 目标架构

导入新算法/功能/策略，对架构无影响，最优性能始终可求解。

架构关注调度，算法，接口三个维度，函数实现是算法的载体，接口是数据传递的媒介，队列/函数名是接口的具象化。

调度框架(EPG)组织算法运行，实现整体性能最优，框架本身支持性能可视化，支持一键生成性能profile，先以级联模式运行一遍，生成性能数据，通过配套求解器求解最优性能，生成最优调度拓扑配置，二次部署生效。

## 不允许违背原则

1. 算法/函数实现要高效精简，最大化利用标准库实现，不允许重复造轮子。
2. 接口要抽象，最大化可复用性，不允许重复实现/代码出现在不同函数中。
3. 功能模块只关注自身算法实现，由调度框架统筹调度，不允许耦合调度内容。
4. 先设计评审好算法/接口，再做调度设计，不允许先设计调度再设计算法/接口。
5. 所有代码/程序都必须经由调度框架统一管理，不允许有游离于调度框架之外的程序运行。
6. 允许模块分层设计，但一个目录下的文件必须是同一类功能/层次，不允许一个模块功能层次分散在不同目录。

## 架构例外

原则 5 的强制范围是机载 native runtime：`smart_drone` 主进程、system EPG、session EPG，以及它们直接承载的闭环感知、控制、通信和状态发布任务。

Android 控制端、离线 replay、离线 regression/test harness 属于外部客户端或离线验证工具，不要求纳入机载 EPG 统一调度。它们不得承载机载闭环运行逻辑；一旦代码路径进入机载 runtime，就必须通过 system/session EPG 管理。
